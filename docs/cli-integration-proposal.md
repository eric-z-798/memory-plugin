# CLI 群聊共享记忆：接入草案

日期：2026-11-04（Asia/Shanghai）

状态：早期设计记录。现已收到用户上传的群聊代码并实现 0.2.0，当前实现与边界以 [需求与实现状态](requirements.md)、[README](../README.md) 为准。本文下列接口为初始提案，不应作为现有 API 文档或已完成能力清单。

## 目标与边界

把共享记忆放在现有 CLI 群聊调度器中，保留现有三家账号接入方式，不新增模型 API 依赖。调度器统一负责调用前检索、上下文装配和调用后记忆写入。记忆核心独立于具体模型与 CLI，以便后续扩展其他入口。

用户此前提出的官方网页、桌面、手机 App 覆盖保留为后续目标。CLI 工具内保存的内容不会自动进入这些独立客户端；它们需要各自的连接器或用户主动交接。本文也不假设 CLI 会话等同于官方聊天产品中的会话。

“长期”指数据可持久保存、备份、恢复和迁移。单轮只能载入预算内的相关记忆。模型账号凭据继续由已有适配器管理，记忆模块不需要保存登录令牌。

## 接入结构

```text
用户输入 / 项目选择
        |
现有群聊调度器 <----> 共享记忆核心 <----> 本地持久存储
        |
        +-- 现有三家适配器：输入上下文、输出消息、管理会话
```

建议首版使用本地 SQLite 保存来源、记忆和版本，Markdown/JSON 用于导出。具体语言和进程模式沿用宿主工程：同语言可直接调用库；否则可采用 JSON Lines 本地子进程协议。这些是建议，待检查源码后决定。

首版以项目过滤、关键词和标签检索为主。中文内容要用合成语料验证短语、子串或实际分词策略，不能假设 SQLite 默认全文分词已经适合中文。向量检索不是首版依赖，也不需要额外的 Embedding API。

## 一轮群聊的读写顺序

1. **记录输入。** 调度器为项目、轮次、调用和事件分配稳定 ID，保存用户原文。
2. **准备快照。** 根据问题与项目权限检索，在版本 R 上生成有预算上限的上下文包，返回来源、版本和截断信息。
3. **分发。** 同一并行轮次共用版本 R。三家可附加不同角色任务，但不能由于回复先后顺序而读到不同版本的持久记忆。
4. **记录输出。** 保存各家输出与完成、失败、取消状态。流式分块带序号，重复投递可去重；部分回答明确标记为不完整。
5. **形成候选。** 用户显式保存的内容、模型提出的新事实和建议分别标记；模型候选不自动成为用户已确认决定。
6. **统一提交。** 调度器提交经规则或用户明确选择的变更，校验基础版本。如果其他轮次已更新该项目，则重读并解决冲突；不能静默覆盖。
7. **下一轮生效。** 有有效变更才产生新版本。失败、取消及无变更轮次不凭空递增有效记忆版本。

如果后一个模型需要看到前一个模型的回答，使用明确的串行子轮次，并记录它实际见过的消息 ID。待讨论的回答可以作为本轮讨论材料传入，但仍保留“模型建议”等来源标签，不能直接提升为有效事实。

## 最小接口草案

以下为逻辑契约，不是已经实现的函数或可执行协议。

| 接口 | 输入要点 | 返回与约束 |
| --- | --- | --- |
| `append_event` | `event_id, project_id, round_id, call_id, actor, content, status` | 追加来源事件；同 ID 同内容幂等，同 ID 不同内容报冲突 |
| `prepare_context` | `project_id, query, session_id, budget` | `snapshot_id, revision, context, source_ids, included_versions, truncated`；项目和权限过滤在检索前完成 |
| `propose_memories` | `source_event_ids, candidates` | 验证来源真实存在且属于授权范围；只创建候选 |
| `commit_memories` | `project_id, base_revision, decisions, idempotency_key` | 原子提交变更，版本不匹配返回冲突；确认依据由宿主用户操作或明确规则提供 |
| `forget` | `project_id, memory_ids, deletion_scope` | 清除选定记忆及衍生内容、使上下文缓存失效；删除范围需区分有效记忆与来源原文 |

同一轮将 `prepare_context` 的结果分发给三家，而不是分别执行三次无版本约束的查询。预算单位由适配器明确声明；无法准确计数时使用保守估计并标注。为用户输入、模型输出及工具结果保留空间。

## 记忆与证据

来源事件保存原始发言者、平台/适配器、会话、轮次和时间；元数据由调度器生成，不信任模型自行宣称的来源。

有效记忆建议包含：`id, project_id, type, content, source_event_ids, status, version, valid_from, supersedes`。类型包含偏好、事实、决定、约束、任务状态；状态包含候选、有效、已替代、冲突和已删除。

区分“谁提出候选”和“候选依据是什么”。Claude 复述 ChatGPT 的猜测，仍然只指向那一条初始猜测；重复转述不增加独立证据。后到的消息也不一定描述更新的事实，不能简单按写入时间覆盖。

用户明确指定的个人偏好和决定可以进入有效记忆；模型摘要仅是派生视图，保留原文引用。提炼失败时保留原始事件，不宣称保存了完整的新记忆。

记忆检索返回的是数据材料，不能把其中的指令自动提升为宿主权限或系统指令。不同项目默认独立；全局偏好须显式设为共享范围。

## 无新增模型 API 的保存与提炼

- 首版可用显式动作，例如拟议的 `/remember`、`/decide`、`/todo`，以及选取消息片段保存。这些命令尚未实现。
- 自动提炼可使用现有 CLI 在正常响应中给出结构化候选，或在轮次结束后由一个现有 CLI 执行一次提炼；先校验格式和来源，再处理候选。
- 这种提炼不需要新增模型 API 接口，但仍消耗已有账号额度和时间；不应宣称免费或无限调用。
- 核心保存、检索、编辑和导出必须能够在提炼模型不可用时继续工作。

## 长会话与恢复

记录每个会话收到的记忆 ID、版本和上下文快照。已知仍保留上下文时，可以注入变更与本次相关内容；如果 CLI 可能压缩历史、重建会话，或宿主无法确认保留范围，则重新提供有长度上限的权威上下文包，不能仅凭“以前发过”省略重要事实。

更新事实时注明替代关系。接近上下文阈值时，用当前有效记忆、当前任务、未完成事项与必要近期原文建立新会话。CLI 是否提供用量、压缩、恢复与新建会话接口，需要检查实际实现，不预设具体参数。

源记录按事件保留，摘要从证据生成，避免一层层摘要丢失限定条件。检索失败、来源缺失或内容被截断时，应向调度器返回明确状态，不能返回看似完整但实际缺失的上下文。

## 删除、备份与跨设备

删除需清理有效记忆、派生摘要、检索索引和缓存。若选择彻底遗忘，也需处理其来源片段，避免再次提炼恢复；多个记忆共享原文时，应按片段或明示范围删除。删除标记与备份保留策略在实现时明确。

外部记忆删除不能撤回已经传入 CLI 历史或官方服务的内容。后续会话需要排除该内容时，建立干净的新会话；第三方历史仍由对应客户端管理。

本地存储不等于跨设备同步。后续若电脑和手机通过同一个群聊服务访问，可将服务端作为统一记忆权威源；多个离线副本则需要专门同步协议。原生官方 App 接入另行验证。

## 首版验收

1. 在一个适配器参与的对话中确认项目 A 的预算为 2 万；下一轮另外两家从同一版本读取此决定及来源。
2. 将预算更新为 3 万，默认上下文提供当前值，旧值仍可通过历史追溯。
3. 项目 B 不检索到项目 A 的信息；用户设置的共享偏好按范围生效。
4. 两个轮次并发修改相同决定，冲突被报告，无静默丢失更新。
5. 三家重复转述同一猜测，不会产生三条独立证据或自动确认为事实。
6. 失败、重试、取消与进程重启不产生重复有效记忆；同一幂等键不同内容被拒绝。
7. 中文问题能检索到准备好的中文合成样本，并记录未命中与截断情况。
8. 删除后在新会话中无法从索引、摘要、缓存或再提炼恢复该内容；第三方历史清理另计。
9. 新会话能用上下文包接续未完成任务；如果无法重现来源或缺少信息，应明确呈现。

## 接入前仍需取得的信息

- 群聊工具的仓库链接或工作区路径、技术栈及运行入口。
- 三家实际调用方式：具体 CLI 子进程、其他客户端封装或浏览器自动化。
- 输入输出协议、串行/并行策略、会话创建与恢复、重试和取消的现有实现。
- 首版数据运行位置，以及未来是否让手机通过该群聊工具访问同一服务。

先以现有源码确认调度钩子，再落地记忆实现；无需为这一步要求用户提供账号密码或登录令牌。
